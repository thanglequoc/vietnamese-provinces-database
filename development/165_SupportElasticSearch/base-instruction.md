# Add Elasticsearch Dataset Export

## Objective

Extend the Vietnamese Provinces Database to support **Elasticsearch** as an additional export format.

The Elasticsearch dataset should follow document-oriented design principles instead of the relational SQL schema. Since Elasticsearch performs best with denormalized documents, each province document should embed all of its wards.

The generated dataset should be optimized for the most common use cases:

- Province dropdown
- Ward dropdown (retrieve all wards of a province with a single query)
- Province and ward search
- Full-text search
- GIS spatial queries (optional GIS index)

Refer to the existing output of MongoDB export for guidance on document structure and field naming conventions.
---

# Dataset Structure

Generate **two Elasticsearch indices**.

## 1. provinces

This is the default index intended for most users.

It contains:

- Province metadata
- Administrative Unit information
- All wards embedded under their parent province
- No GIS geometry

Example hierarchy:

```text
Province
├── Metadata
├── AdministrativeUnit
├── SearchKeywords
└── Wards[]
      ├── Metadata
      ├── AdministrativeUnit
      └── SearchKeywords
```

Each province should be exported as a single Elasticsearch document.

Each ward should be embedded inside its parent province.

Do not create separate province and ward indices.

Do not use Elasticsearch parent-child relationships.

---

## 2. provinces-gis

This index contains the exact same document structure as `provinces`.

Additionally, include GIS information for both provinces and wards.

Example hierarchy:

```text
Province
├── Metadata
├── AdministrativeUnit
├── GIS
└── Wards[]
      ├── Metadata
      ├── AdministrativeUnit
      └── GIS
```

The non-GIS fields should remain identical between both indices.

---

# Administrative Unit

Do not export only `AdministrativeUnitId`.

Instead, embed the complete Administrative Unit object.

Example:

```json
{
  "Id": 3,
  "CodeName": "ward",
  "ShortName": "P.",
  "ShortNameEn": "Ward",
  "FullName": "Phường",
  "FullNameEn": "Ward"
}
```

This makes every document self-contained and avoids additional lookups.

---

# GIS Structure

Store GIS information inside a dedicated `GIS` object.

Example:

```json
"GIS": {
  "Center": {
    "lat": 21.0285,
    "lon": 105.8542
  },

  "BoundingBox": {
    "MinLongitude": ...,
    "MinLatitude": ...,
    "MaxLongitude": ...,
    "MaxLatitude": ...
  },

  "Geometry": {
    "type": "MultiPolygon",
    "coordinates": [...]
  }
}
```

Requirements:

- Geometry must use GeoJSON format.
- Reuse the existing GeoJSON export generated by the project.
- Do not convert geometry into WKT.

---

# Search Keywords

Both province and ward should include a precomputed `SearchKeywords` array.

Example:

```json
[
  "01",
  "ha noi",
  "hanoi",
  "ha_noi"
]
```

This field is intended for efficient autocomplete and search.

---

# Version Metadata

Every exported document should include a metadata object.

Example:

```json
"_meta": {
  "DatasetVersion": "2026.07.01",
  "AdministrativeRevision": "2025-07-01",
  "GeneratedAt": "2026-07-18T08:00:00Z"
}
```

Purpose:

- Allow consumers to identify the exact dataset version.
- Improve traceability between releases.
- Make synchronization easier for downstream applications.

---

# Elasticsearch Mapping

Generate mapping files for both indices.

## provinces

Recommended mapping:

- Code → keyword
- ProvinceCode → keyword
- CodeName → keyword
- SearchKeywords → keyword

- Name → text + keyword
- NameEn → text + keyword
- FullName → text
- FullNameEn → text

- Wards → nested

AdministrativeUnit should be mapped as an object.

---

## provinces-gis

Reuse the mapping above.

Additionally:

- GIS.Center → geo_point
- GIS.Geometry → geo_shape
- GIS.BoundingBox → object

The Wards.GIS mapping should follow the same structure.

---

# Output Files

Generate the following output:

```text
elasticsearch/
├── README.md
├── mappings/
│   ├── provinces.json
│   └── provinces-gis.json
├── provinces.ndjson
└── provinces-gis.ndjson
```

The NDJSON files must be directly compatible with the Elasticsearch Bulk API.

---

# Design Principles

- Optimize for read performance rather than storage size.
- Prefer denormalized documents over relational structures.
- Keep every document self-contained.
- Avoid joins and parent-child relationships.
- Keep the document structure consistent with the MongoDB export whenever possible.
- The `provinces` and `provinces-gis` indices should share the same logical schema, with GIS fields being the only difference.
